# PORT — Java to Go Translation Rules

**Status:** Active · **Applies to:** every unit ported from `forge-core`, `forge-game`, `forge-ai` **Rule IDs:** cite as
`PORT-n`

Normative mapping. Read before touching a Java file. Deviating from a rule is allowed — recording the deviation in the
unit's `port-log/` note is not optional.

---

## Core stance

**Port behavior, not structure.**

Java structure came from 15 years of Java constraints: reflection-based dispatch, checked exceptions, mutable
singletons, deep hierarchies, 8,000 lines of accessors. None of those constraints exist in Go. Transliterating them
produces slow, unidiomatic, untestable Go that is harder to fix than the original.

**Test that behavior is preserved** — differential harness (ADR-0010). That is what makes aggressive restructuring safe.

## PORT-1 — Translation table

| Java                                                           | Go                                                                                                  | Trap                                                                        |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `abstract class SpellAbilityEffect` + 205 subclasses           | `Effect` interface + embedded `BaseEffect` struct for helpers                                       | Do not fake inheritance with a type switch on a mega-struct                 |
| Enum with behavior (`ApiType` → class by reflection)           | `type APIType uint16` + generated registry array                                                    | Registry generated by `go:generate` from the enum so it cannot drift (GO-4) |
| `SpellAbility → Spell / AbilityActivated / AbilitySub`         | One `SpellAbility` struct + `Kind` discriminator; behavior via `Effect`                             | Hierarchy is shallow-but-wide; flattening removes ~40 near-empty types      |
| `null`                                                         | Zero value; pointer or `(T, bool)` only where absence is meaningful                                 | Every null is a decision. Log it (GO-11)                                    |
| Checked / unchecked exceptions                                 | `error` for script-caused failures; `panic` only for engine invariants                              | Bad card must not kill the batch (GO-7)                                     |
| Guava `FCollection<T>`                                         | `collect.OrderedSet[T]`                                                                             | Iteration order is load-bearing. Bare `map` breaks replay parity (GO-12)    |
| Guava `Multimap` / `Iterables` / `Predicates`                  | `map[K][]V`, `collect.Filter`, plain loops                                                          |                                                                             |
| `Map<String,String>` ability params                            | Generated typed param struct per API                                                                | #1 silent-bug source in Java. Typing them is the point (GO-8)               |
| Object identity (`==` on `Card`)                               | `CardID uint32` into a per-`Game` arena                                                             | Cards are copied and LKI-snapshotted; pointers lie (GO-9)                   |
| `equals` / `hashCode`                                          | Value types only (`ManaCost`, `ColorSet`, `TypeLine`)                                               | Never on `Card`, `Player`, `Game`                                           |
| Static utility classes (`ComputerUtilCard`, `CardFactoryUtil`) | Package-level funcs in narrow packages (`ai/eval`, `card/build`)                                    | No `util` package (GO-10)                                                   |
| Mutable static singletons (`StaticData`, `FModel`, `MyRandom`) | **Banned.** Inject `*carddb.DB`, `*javarand.Rand` via `*Game`                                       | Highest-probability porting bug (GO-2)                                      |
| `synchronized`, `ThreadUtil`                                   | Nothing. Engine shares only immutable data                                                          | Mutex in engine = design bug (GO-3)                                         |
| Generics `<T extends GameEntity>`                              | Type params with interface constraint                                                               | Clean 1:1                                                                   |
| Anonymous / inner classes                                      | Closures; named struct if it holds state                                                            |                                                                             |
| Getter/setter pairs                                            | Exported field unless there is an invariant                                                         | Do not port 8,000 lines of accessors (GO-13)                                |
| `toString()`                                                   | `String()` on value types; `debug.DumpGame` for state                                               |                                                                             |
| Runtime string interpretation of card scripts                  | **Compile once at load to typed AST**                                                               | Biggest structural divergence. See PORT-2                                   |
| `Card.java`, 8,105 LOC                                         | Split: `card.Card`, `card.State`, `card.Counters`, `card.Attachments`, `card.Damage`, `card.Memory` | Explicit deviation. Record in port-log                                      |

## PORT-2 — Compile scripts, do not interpret them

Java re-parses `A:`/`T:`/`S:`/`SVar:` strings **per card instance, per game**, through `AbilityFactory` and reflection.

Go parses each script **once at load**, into an immutable typed AST shared read-only by every game.

```text
.txt  →  line parse (carddb/script)  →  typed AST (carddb/compile)  →  shared, immutable
                                                                          ↑
per-game Card{ID, zone, counters, damage, ...} ---- pointer ---------------┘
```

Reason: 10⁵–10⁶ games. Re-parsing is the single largest waste in the Java engine.

**Do not "faithfully" port the string interpretation.** Reviewer rejects it on sight.

## PORT-3 — Port order inside a unit

1. Read the Java file end to end. Do not start translating at line 1.
2. Write the `port-log/<unit>.md` note: what it does, what its real inputs and outputs are, which parts are Java
   scaffolding.
3. Write the Go public API for the package (TEST-4 unit).
4. Write module-level tests / fixtures against that API (TEST-1) — before the implementation body.
5. Implement.
6. Run differential harness against the Java oracle (ADR-0010).
7. Update `porting/parity-matrix.md`.

Step 2 is where structural decisions get made. Skipping it produces transliteration.

## PORT-4 — port-log note format

One file per ported unit: `docs/crucible/porting/port-log/<unit>.md`.

```text
# Port: GameAction.checkStateEffects

**Java source:** `forge-game/src/main/java/forge/game/GameAction.java:1204-1890`
**Go target:** `crucible/internal/engine/game/sba.go`
**Status:** Done | In progress | Blocked

## What it does

State-based actions + continuous-effect layer application pass. Runs on every priority gain and after every resolution.

## Deviations from Java

- Split into `applyLayers()` + `checkSBA()`. Java interleaves them; separating makes layer ordering testable in
  isolation (CR 613 fixtures).
- `Card.isCreature()` re-derived per call in Java. Go caches per layer pass, invalidated by timestamp bump.

## Null decisions

- `getTopCard()` returns null on empty library -> Go `(CardID, bool)`.

## Open questions

- Java runs the loop twice in some paths. Reason unclear. Fixture `cr704-double-pass/` pins current behavior; revisit
  at M6.
```

Reason: in six months nobody remembers why Go diverged. Note is the only defence against a "fix" that reintroduces a
Java quirk.

## PORT-5 — Behavior parity is the gate, not code similarity

A Go unit is done when:

1. Module tests pass (TEST-1).
2. Fixtures pass, including edge and interaction cases (TEST-5).
3. Differential harness green against Java for the covered scenarios (ADR-0010).
4. `parity-matrix.md` row updated.
5. port-log note merged.

"Looks like the Java" is not a criterion. "Produces the same observable behavior" is.

## PORT-6 — Do not port

| Java                                                             | Why not                        |
| ---------------------------------------------------------------- | ------------------------------ |
| GUI modules (`forge-gui-desktop`, `-mobile`, `-android`, `-ios`) | No UI in Crucible              |
| `forge/net/*` and its tests                                      | No network play                |
| Adventure, Quest, Conquest, Puzzle, Draft/Sealed modes           | Out of scope. Constructed only |
| Localization (`Localizer`, `res/languages`)                      | English-only tool              |
| Image download, sound, skins                                     | No assets                      |
| Achievements, card art, `forge-lda`                              | Not needed                     |

Anything on this list showing up in a PR needs an ADR first.

## PORT-7 — Java quirks: pin, then decide

Java has behavior that is neither documented nor obviously intended (double-passes, ordering side effects, defensive
re-checks).

Procedure:

1. **Pin it.** Write a fixture that captures current Java behavior. Go matches it.
2. **Log it.** port-log "Open questions" section.
3. **Decide later.** At M6, review pinned quirks: real rule, or Java bug?

Do not "fix" a quirk during the port. Fixing changes behavior while you are trying to prove behavior is unchanged, and
you lose the only signal you have.
